# Security Specification: Universal Attendance & GPS Tracker

## 1. Data Invariants
- A worker can only mark attendance if they are signed in and have a `companyCode`.
- Workers can only read and write their OWN attendance records.
- Admins can read and write attendance records for any worker that has their `companyCode`.
- A company code is permanent and generated by an Admin.
- Messages can only be read by the sender or receiver.
- Attendance IDs are strictly formatted as `{userId}_{YYYY-MM-DD}`.

## 2. The "Dirty Dozen" Payloads
1. **Identity Theft**: Mark attendance for another `userId`.
2. **Role Escalation**: Attempt to set `role: 'admin'` during self-signup.
3. **Teleportation**: Spoof `lat/lng` (Client-side, handled by logic but rules should at least check types).
4. **Time Travel**: Attempt to set `checkInTime` to a future or past date (Must be `request.time`).
5. **Admin Spoofing**: Attempt to set `modifiedByAdmin: true` as a worker.
6. **Company Takeover**: Create a company with someone else's `code`.
7. **Message Prying**: Read messages where `senderId` or `receiverId` is not the current user.
8. **Shadow Fields**: Add a `isVerified: true` field to the user profile.
9. **Spam Attack**: Send messages to a user in a different company.
10. **ID Poisoning**: Use a 2KB string as a `companyCode` or `userId`.
11. **Outcome Manipulation**: Change a status from 'absent' to 'present' after it was manually set by admin (Admin only).
12. **Ghost Record**: Create attendance for a date that doesn't exist (format validation).

## 3. Test Runner (Draft Rules)
The test runner will verify that:
- `create` on `/users/{uid}` fails if `uid != request.auth.uid`.
- `update` on `role` fails for workers.
- `write` on `/attendance` fails if `userId != auth.uid` AND user is not the admin of that company.
